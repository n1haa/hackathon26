# CashFlow AI

Модуль `forecasting` прогнозирует дневные поступления и расходы и рассчитывает
остаток на следующие 30 дней. Модуль `transaction_classifier` использует
предоставленный код классификации операций. Backend, risk engine, поиск регулярных
платежей, frontend и банковские интеграции в этой папке отсутствуют.

## Запуск

Python 3.10+. В PowerShell из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[test]'
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m forecasting.demo
```

В Linux/macOS используйте `.venv/bin/python`. Демо сохраняет явно синтетические
операции, метаданные покрытия, сравнение моделей и прогноз в
[`artifacts/synthetic_demo`](artifacts/synthetic_demo). Реального датасета в проекте нет.
Версии проверенного окружения приведены в [`requirements-tested.txt`](requirements-tested.txt).
Для повторения окружения: сначала `python -m pip install -r requirements-tested.txt`,
затем `python -m pip install --no-deps -e .` (команды выполняются внутри venv).

## Использование в backend

```python
from transaction_classifier import classify_transactions
from forecasting import forecast_cashflow

operations = [
    {"date": "2026-10-23T10:00:00+03:00", "amount": 15000,
     "direction": "incoming", "purpose": "Оплата за услуги",
     "closing_balance": 85000},
    {"date": "2026-10-24T11:00:00+03:00", "amount": 5000,
     "direction": "outgoing", "purpose": "Аренда помещения",
     "closing_balance": 80000},
]
classified = classify_transactions(operations)
result = forecast_cashflow(
    classified,
    current_balance=80000,  # консолидированный остаток на конец as_of
    horizon=30,
    as_of="2026-10-24",
    history_start="2026-10-23",
    opening_balance=70000,
    complete_history=True,  # только если выписка действительно полная
)
# result — обычный dict, пригодный для JSON-ответа backend и передачи risk engine
assert len(result["forecast"]) == 30
```

`forecast_cashflow(transactions, current_balance, horizon=30)` принимает список
словарей или DataFrame. Остальные параметры именованные. Классификатор вызывается
командой отдельно: forecasting использует готовые категории и не классифицирует
назначение повторно. При отсутствии категории поток учитывается как `unknown`.
Параметр `fields={"date": "Дата", "amount": "Сумма", ...}` адаптирует имена полей.

### Контракт входа

| Поле | Смысл |
| --- | --- |
| `date` | Дата/время операции, ISO-строка или datetime. Числовые даты запрещены |
| `amount` | Неотрицательная конечная сумма, максимум два знака после запятой; допустимы строки Decimal |
| `direction` | `incoming` / `outgoing`, также `поступление` / `списание` |
| `category` | Готовая категория классификатора, необязательна |
| `closing_balance` | Необязательный остаток **после этой операции** |
| `account_id` | При наличии — непустой ID счёта; `closing_balance` тогда относится к этому счёту |
| `transaction_id` | Необязательный уникальный ID; дубликаты вызывают ошибку |
| `recurring_id` | Необязательный ID серии от внешнего детектора регулярных платежей |
| `company_id`, `currency` | При наличии все строки должны относиться к одной компании и одной валюте |

Направление хранится отдельно: отрицательная `amount` вызывает ошибку. Отрицательные
чистый поток, текущий и прогнозный остатки допустимы. Forecasting допускает нулевые
суммы; существующий классификатор требует положительные и может вернуть `unknown`.
Вычисление баланса и сверка выполняются через Decimal с точностью до копейки;
статистические/ML-вычисления используют float. Прогнозные потоки округляются до
копеек перед накоплением остатка. В JSON денежные поля представлены числами.

`timezone="Europe/Moscow"` задаёт календарь бизнеса: timezone-aware даты сначала
переводятся в этот пояс; naive даты считаются локальными. `as_of` — последний
полностью наблюдаемый день истории. Без него используется дата последней операции,
поэтому для выписки с последующими днями без операций передавайте `as_of` явно.
Прогноз начинается на следующий календарный день. `generated_at` — время формирования
в UTC, отдельно от даты исторического среза. Данные после `as_of` отклоняются.

### Покрытие выписки и остатки

Операции сортируются по времени; при совпадающем времени сохраняется входной порядок.
Для дат без операций ноль допустим только при `complete_history=True` или явном
`observed_dates=[...]`. Без этих параметров даты с операциями считаются наблюдаемыми,
а пустые даты остаются NaN. `prepare_daily_cashflows` возвращает такой календарь и
предупреждения; прогноз и оценка отказываются обучаться на неизвестных днях.
`history_start` позволяет включить начальные дни без операций. За полноту дней с
операциями и отсутствие частичной загрузки отвечает поставщик выписки.

`internal_transfer` исключается из доходов и расходов консолидированного бизнеса.
Признак должен быть подтверждён внешним классификатором/парсером. Переводы по
совпадающим суммам не угадываются. Комиссии должны идти отдельными внешними расходами.
При нескольких счетах upstream должен предоставить полный набор счетов одного
бизнеса, одну валюту и согласованный консолидированный `current_balance`.

При наличии `account_id` остатки сверяются по каждому счёту с учётом собственных
переводов. Без него остатки считаются консолидированными, собственные переводы не
меняют их. `opening_balance` задаётся до начала истории и поддерживается для одного
счёта/консолидированного потока. Первый снимок без начального остатка полностью
проверить нельзя; последующие проверяются с учётом промежуточных операций. Сумма
последних восстановленных остатков счетов сравнивается с `current_balance`.

Несовпадение даже на копейку попадает в `warnings`; функция прогноза также выдаёт
Python `ForecastWarning`. При недостаточных снимках возвращается предупреждение
о невозможности полной сверки. Прогноз всегда использует переданный `current_balance`:
ошибка этого значения сдвигает все прогнозные остатки; потерянные операции могут
также исказить обученные потоки. Расхождения не исправляются скрыто.

### Контракт результата для risk engine

```python
{
    "model_name": "weekday_baseline",
    "horizon": 30,
    "as_of": "2026-10-24",
    "generated_at": "...+00:00",
    "timezone": "Europe/Moscow",
    "current_balance": 80000.0,
    "history_days": 2,
    "forecast": [{
        "date": "2026-10-25",
        "predicted_income": 7500.0,
        "predicted_expense": 2500.0,
        "predicted_net_flow": 5000.0,
        "predicted_balance": 85000.0,
        "model_income": 7500.0, "model_expense": 2500.0,
        "scheduled_income": 0.0, "scheduled_expense": 0.0,
    }],  # здесь сокращено: в ответе ровно horizon последовательных записей
    "metrics": {"status": "insufficient_history", "...": "..."},
    "warnings": ["..."],
    "recurring_events": [],
}
```

Остаток не обучается как отдельная цель:

```text
predicted_net_flow[t] = predicted_income[t] - predicted_expense[t]
predicted_balance[t] = predicted_balance[t-1] + predicted_net_flow[t]
predicted_balance[0] = current_balance + predicted_net_flow[0]
```

Risk engine получает дневные остатки, разделение модели и расписания, предупреждения
о данных и метрики. Решения о кассовых разрывах принимает отдельный модуль команды.
Общей backend-схемы в предоставленных файлах нет: этот контракт опирается на поля
существующего классификатора, но ещё требует подключения к фактическому backend.

## Модели и проверка качества

1. `weekday_baseline`: историческое среднее отдельно по дням недели. Для ещё не
   встречавшихся дней недели используется общее среднее.
2. `exponential_smoothing`: отдельный уровень простого экспоненциального сглаживания
   для каждого дня недели, фиксированный `alpha=0.3`. Это статистическая модель
   недельной сезонности, без автоматической подгонки ETS или праздничного календаря.
3. `hist_gradient_boosting`: два HistGradientBoostingRegressor для доходов/расходов;
   календарь, лаги 1/7/14/28, предыдущие средние и суммы за 7/28 дней, прошлые
   категорийные потоки. Минимум 56 полных дней. Early stopping отключён; случайного
   перемешивания/validation split внутри модели нет.

Все лаги и окна строятся из `shift(1)` либо более ранних значений; текущая цель в
признаки не попадает. ML строит многодневный прогноз рекурсивно, подставляя только
собственные предыдущие прогнозы. Категорийные будущие потоки аппроксимируются
долями из train. В каждом обучении используются только категории с ненулевой
историей до текущего среза. Новые будущие категории в train не раскрываются.
Отрицательные прогнозы доходов/расходов обрезаются до нуля.

`evaluate_models(daily, horizon=30)` использует последовательное разделение:
train → до трёх непересекающихся expanding walk-forward validation-окон → test.
Каждое окно и конечный test имеют длину `horizon`; минимум train — 56 дней. Для
полной оценки на 30 дней нужно не менее 116 дней истории. При меньшем количестве
`auto` честно возвращает baseline и `status="insufficient_history"`, без метрик.
Пустая история или неизвестное покрытие дают понятный ValueError.

Выбирается модель с минимальным `validation.flow_mae`, то есть средним MAE доходов
и расходов. При равенстве сохраняется baseline. MAE остатка также возвращается,
но не является критерием выбора: лучшая модель потоков может быть хуже по остатку.
Test не влияет на выбор. Для конечного прогноза выбранная модель обучается заново
на всей доступной истории. Метрики относятся к историческим отложенным окнам,
а не к ещё неизвестным следующим 30 дням.

Возвращаются MAE, RMSE и WAPE каждого потока, общий `flow_mae` и MAE остатка.
WAPE — доля (`0.1` = 10%); при нулевой сумме факта возвращается `None`/JSON `null`.
Ошибки остатка накапливаются из потоков и сбрасываются в начале каждого окна.
Метрики остатков измеряют ошибку потоков при известном начальном балансе, не ошибки
самого начального снимка. Остатки выписки не используются как независимая цель.
`model="..."` позволяет явно запросить модель, однако это не меняет результат
сравнения в `metrics`. Принудительный ML при недостатке истории вызывает ошибку.

Документация использованных API:
[HistGradientBoostingRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html),
[DataFrame.shift](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.shift.html).

## Регулярные платежи: интерфейс для модуля Саши

Детектор регулярности не реализован. По умолчанию вся история прогнозируется как
исторический поток. Для явного расписания нужно передать обнаруженные события и
пометить соответствующие исторические операции одним `recurring_id`:

```python
transactions = [
    {"date": "2026-10-05", "amount": 25000, "direction": "outgoing",
     "category": "rent", "recurring_id": "rent-office"},
    {"date": "2026-10-24", "amount": 5000, "direction": "incoming",
     "category": "revenue"},
]
events = [
    {"event_id": "rent-office-2026-11-05", "recurring_id": "rent-office",
     "date": "2026-11-05", "amount": 25000, "direction": "outgoing"},
]
result = forecast_cashflow(
    transactions, current_balance=80000, as_of="2026-10-24",
    complete_history=True, recurring_events=events,
)
```

Связанные исторические потоки исключаются **до обучения и оценки**, а явные события
добавляются в назначенные дни. Поэтому аренда не учтётся дважды. Передавайте полное
расписание в пределах горизонта для всех исторических `recurring_id`; отменённую
серию можно явно представить событием с нулевой суммой. Каждый ID серии должен иметь
одно направление. Дубликаты `event_id` и одной пары серии/даты/направления запрещены.
События вне горизонта и внутренние переводы отклоняются.

Для новой серии без исторических операций требуется явное `is_new=True`.
Это утверждение детектора/поставщика, что событие действительно новое; нельзя
использовать его для старой, но не размеченной серии. Полнота исторической привязки
остаётся ответственностью детектора. При `None`/пустом списке событий история не
меняется. Безопасного автоматического связывания по названию, категории или сумме нет.
События приходят от команды, вымышленные обязательства не генерируются.

При переданном расписании `metrics.scope="residual_flows_without_recurring_series"`:
метрики характеризуют остаточный исторический поток, а не точность внешнего расписания.

## Измеренный результат на синтетических данных

Команда `python -m forecasting.demo` реально обучила/проверила все три модели.
Генератор: seed=42, 240 дней, 2026-01-01…2026-08-28; вымышленный бизнес в RUB,
недельная сезонность, тренд, шум, аренда и подтверждённые дни без операций.
Сверка синтетических остатков не обнаружила расхождений.

Validation: три окна по 30 дней, 2026-05-01…2026-07-29, с расширением train.
Test: 2026-07-30…2026-08-28. Сглаживание выбрано **по validation**.

| Модель | Validation flow MAE, ₽ | Test MAE доходов, ₽ | Test MAE расходов, ₽ | Test flow MAE, ₽ | Test MAE остатка, ₽ |
| --- | ---: | ---: | ---: | ---: | ---: |
| Weekday baseline | 1655.14 | 2125.77 | 1661.37 | 1893.57 | 12364.63 |
| Exponential smoothing | **1370.35** | 1457.16 | 1765.37 | **1611.26** | **7059.39** |
| HistGradientBoosting | 1846.78 | 2011.12 | 1516.30 | 1763.71 | 10442.24 |

ML хуже baseline на validation по критерию выбора, поэтому не выбран. На test
выбранное сглаживание уменьшило общую ошибку потоков, но MAE расходов вырос.
Полные RMSE, WAPE, метрики каждого окна, даты разбиений и ошибки обучения сохранены в
[`evaluation.json`](artifacts/synthetic_demo/evaluation.json). Итоговый прогноз после
обучения на всех 240 днях — [`forecast.json`](artifacts/synthetic_demo/forecast.json).
Эти измерения проверяют реализацию на синтетике и не доказывают качество на реальных
банковских данных. Подбора параметров по test не проводилось.

## Проверки и ограничения

Pytest проверяет разные горизонты, короткую/нулевую историю, отрицательный чистый
поток и остатки, неизвестные и явно пустые дни, timezone, сортировку, ошибки сумм,
сверку остатков до копейки, собственные переводы, формулу баланса, причинность
признаков, временные границы, выбор по validation, три реальные модели, регулярные
события без двойного учёта, JSON и подключение исходного классификатора.

Реальный датасет, парсер выписок, backend-схемы и детектор регулярности не были
предоставлены. Входные поля взяты из имеющегося README классификатора. Модель
предназначена для одного бизнеса/валюты и не учитывает курсы, праздники, планы продаж,
неизвестные обязательства или структурные изменения бизнеса. Нет интервалов
неопределённости. Длинный рекурсивный прогноз может накапливать ошибку.
История должна быть полной; без transaction_id произвольные дубликаты не угадываются.
Функция переобучает модели при вызове; кэширование/фоновое обучение остаётся backend.
На больших данных категорийные признаки увеличивают стоимость вычислений.

Исходные файлы были перепутаны: `pyproject.toml` содержал код классификатора,
`__init__.py` — ML, `core.py` — правила, `rules.py` — экспорты. Их содержимое без
изменения логики собрано соответственно в `transaction_classifier/core.py`, `ml.py`,
`rules.py`, `__init__.py`. Восстановлен настоящий pyproject; корневой `__init__.py`
стал нейтральным. Корневые `core.py`, `rules.py`, `README (1).md` и ошибочно названный
`test_classifier (1).py` сохранены как входные материалы; последний содержит README,
поэтому настоящие тесты находятся в `tests/` и только оттуда собираются pytest.
